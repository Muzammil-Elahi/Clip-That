## 1. System Classification

**System Type:** Hybrid (Semantic Retrieval — embedding + cosine similarity scoring, no agent orchestration)

**Description:**
An optional semantic retrieval module that embeds a student-supplied study topic and each transcript segment from a YouTube lecture into a shared vector space, then ranks segments by cosine similarity and promotes those above a calibrated threshold into the clip plan alongside any exact matches. The module is stateless, single-function, and runs only when the student explicitly opts in via a toggle. Its output is a ranked list of `ClipMatch` objects annotated with `matchType: 'semantic'` and a numeric confidence score; the downstream video stitcher and study-notes generator consume this output without knowing which matching mode produced it.

**Critical Failure Modes:**
<!-- The 3-5 behaviors that absolutely cannot go wrong in this system -->
1. Semantic failure breaks the whole job — an embedding API error or threshold miscalibration must never prevent exact-match results from being returned to the student. Soft-fail is mandatory.
2. Topically unrelated segments are included at high confidence — a segment about a different STEM discipline scores above threshold and appears in the stitched video, sending the student to study irrelevant material. This is the primary quality hazard for this use case.
3. Semantic matches duplicate exact-match segments — the same segment appears twice in the clip plan, inflating video length and confusing the transcript without adding information.
4. The opt-in toggle silently defaults to enabled — a student who did not choose semantic matching receives semantically matched clips without knowing it, undermining the "exact-match is the safe default" contract.
5. Confidence scores are displayed without calibration — a raw cosine similarity of 0.76 displayed as "76% confident" implies a precision the model does not have; students may over-trust or misinterpret the indicator.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Educational technology — self-directed video study tool for learners using YouTube lecture and tutorial content.

**User Population:** Students and self-directed learners studying STEM, humanities, or professional development topics via YouTube lectures, educational talks, and tutorials. Anonymous (no accounts in v1). Predominantly post-secondary age but the tool imposes no age gate.

**Stakes Level:** Medium — incorrect matches waste study time and produce a confusing clip reel; missing a relevant segment is an opportunity cost. No safety, financial, or medical consequences.

**Output Consequence:** Semantically matched segments are stitched into the student's video and included in the transcript and study notes they download. A false positive (irrelevant clip included) actively misleads the student's understanding of the topic they searched. A false negative (relevant clip missed) means the student may not encounter a useful explanation — they can always rewatch the full video, so it is a missed convenience, not a critical error.

### What Domain Experts Evaluate Against

```
Dimension: Conceptual relevance to the search topic
Good: The matched segment addresses the same underlying concept as the student's topic — e.g., a segment about "loss function minimization" is correctly included when the student searched "gradient descent", because an instructional designer would mark these as the same learning objective.
Bad: The matched segment discusses a concept from the same general domain (e.g., "neural networks" when searching "gradient descent") but does not address the topic — an instructional designer would classify it as adjacent, not relevant.
Stakes: High
Source: Instructional design practice — Bloom's Taxonomy and learning-objective alignment distinguish "same concept" from "same subject area"; practitioners evaluate whether a clip would appear in a targeted study guide for that specific topic.
```

```
Dimension: Absence of cross-discipline false positives
Good: Searching "photosynthesis" in a biology lecture returns only segments that explain the photosynthesis process; segments about plant cell structure that do not mention energy conversion are excluded.
Bad: Searching "gradient descent" in a machine learning lecture returns a segment from an economics section about "descending price curves" — the word overlap triggers a false match that an educator would immediately flag as off-topic.
Stakes: High
Source: Semantic search evaluation research (arxiv.org 2410.21549) identifies "on-topic rate" as the primary practitioner metric — the proportion of retrieved results genuinely addressing the query concept, not merely sharing vocabulary.
```

```
Dimension: Proportionality of matched content to the topic scope
Good: A narrow topic like "softmax function" returns 2–4 short, focused segments. A broad topic like "deep learning" returns up to the 10-segment cap, each contributing a distinct sub-concept.
Bad: A narrow topic returns 10 segments — the cap is hit by including low-relevance filler — or a broad topic returns only 1 segment because the threshold is set too high, giving the student an incomplete picture.
Stakes: Medium
Source: Educational video research (arxiv.org 2405.12540) finds that clip length and count directly affect learning utility; clips under ~12 seconds rarely convey a complete concept, while excessive clips cause cognitive overload.
```

```
Dimension: Exact-match integrity preserved when semantic mode is on
Good: Every segment already found by exact matching appears in the final clip plan, and semantic matches supplement rather than replace them. A student searching "gradient descent" who opted in sees all direct mentions plus any semantically related segments.
Bad: Semantic deduplication logic incorrectly removes a segment found by exact match, or a high-confidence semantic match suppresses an exact match lower in the ranked list — the student loses the most literal answer to their query.
Stakes: Critical
Source: Clip-That product requirement MAT-03 — exact and semantic matches must be kept separate and cumulative; the exact-match default is the product's reliability guarantee.
```

```
Dimension: Confidence indicator honesty
Good: A segment labeled as a semantic match with a displayed confidence indicator is visibly distinguished from an exact match, and the confidence value reflects relative rank among semantic results (e.g., "top match" vs. "related") rather than implying absolute percentage precision.
Bad: A raw cosine similarity score of 0.76 is displayed to the student as "76% match" — the student interprets this as a validated accuracy percentage and trusts a borderline result more than the system's calibration warrants.
Stakes: Medium
Source: Human-computer interaction research on algorithmic transparency in learning tools — students systematically over-trust numeric confidence scores when they are presented without context (EduGenius / EdTech compliance guidance, 2025).
```

### Known Failure Modes in This Domain

1. **Surface vocabulary overlap without conceptual alignment.** Embedding models encode token co-occurrence patterns; two segments can have high cosine similarity because they share domain vocabulary (e.g., both mention "function" and "curve") while addressing completely different concepts. Educational content is especially susceptible because lectures use the same technical vocabulary repeatedly across unrelated sub-topics.

2. **Adjacent-concept inflation.** A topic like "gradient descent" semantically neighbors "backpropagation", "learning rate", "loss function", and "optimization" — all of which may score above threshold. A student studying gradient descent specifically gets a clip reel that covers an entire ML curriculum sub-tree. This is a precision problem: each individual match is defensible, but the aggregate output has drifted from the stated topic.

3. **Threshold miscalibration by content type.** The optimal cosine similarity threshold varies significantly by lecture style: a highly structured textbook-narration lecture (dense, precise vocabulary) produces tight embedding clusters and may require a threshold of 0.80+, while a conversational tutorial with tangents and colloquial language produces noisier embeddings and may require 0.70. A single fixed threshold produces too many false positives in one context and too many false negatives in the other.

4. **Exact-match bypass when semantic mode is on.** If the deduplication logic contains a bug — e.g., it compares segment indices rather than segment text, and an index shift occurs after filtering — an exact-match segment may be silently dropped from the final clip plan. The student searches a term that is spoken verbatim in the video and does not see it in their stitched output, an error that undermines the core reliability guarantee.

## 2. Framework Decision

**Selected Framework:** No framework — direct `@google/genai` SDK v2.10.0

**Version:** @google/genai v2.10.0 (already installed in worker/)

**Rationale:**
Phase 06 requires a single exported function (`worker/src/semanticMatcher.ts`) that calls `embedContent()` via the Gemini text-embedding-004 model and computes cosine similarity over an already-structured array of `TranscriptSegment` objects. There is no agent loop, no stateful workflow, no document ingestion pipeline, and no multi-step orchestration — every framework in the decision matrix adds abstraction overhead that solves problems that do not exist here. The SDK is already installed in `worker/package.json`, the import pattern is already established in `worker/src/notesGenerator.ts`, and the existing `GEMINI_API_KEY` credential covers it with no additional config. No new credentials, no new infrastructure.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LlamaIndex TypeScript SDK | Overkill — its strength is document ingestion pipelines, not single-function cosine similarity over an already-structured segment array. Adds a new dependency with no benefit at this scope. Best upgrade path if scope later expands to vector store persistence or multi-model retrieval. |
| Google ADK | Python/Java only — incompatible with the TypeScript/Node.js worker. Also multi-agent orchestration; this use case needs a single function. |
| LangChain TypeScript | Anti-pattern: direct SDK call is less code, faster, and easier to debug than wrapping a simple embeddings call in a chain. |
| LangGraph | Stateful graph overhead for a single function — explicit anti-pattern per framework matrix. |
| CrewAI | Python only. Also multi-agent; not applicable. |

**Vendor Lock-In Accepted:** Partial — Gemini embeddings (text-embedding-004) are already committed via CONTEXT.md D-01. Switching embedding models would require changing only the model name string and recalibrating the cosine threshold. The `@google/genai` SDK is the same vendor lock-in already accepted in Phase 5 for note generation.

### Entry Point Pattern
```typescript
// Embed a single string — returns a number[] of 768 floats (gemini-embedding-001 default)
async function embedText(text: string): Promise<number[]> {
  const response = await ai.models.embedContent({
    model: 'gemini-embedding-001',          // text-embedding-004 shut down Jan 14 2026
    contents: [text],                        // array — even for a single string
    config: { taskType: 'SEMANTIC_SIMILARITY' },
  })
  // response.embeddings is ContentEmbedding[] — access values on first element
  const values = response.embeddings?.[0]?.values
  if (!values) throw new Error('embedContent returned no embedding values')
  return values                              // number[], length 768
}

// Cosine similarity — pure math, no library needed
function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, magA = 0, magB = 0
  for (let i = 0; i < a.length; i++) {
    dot  += a[i] * b[i]
    magA += a[i] * a[i]
    magB += b[i] * b[i]
  }
  if (magA === 0 || magB === 0) return 0
  return dot / (Math.sqrt(magA) * Math.sqrt(magB))
}

// Batch embed multiple segments — stay inside 1500 RPM free-tier ceiling.
// gemini-embedding-001 accepts multiple strings in one contents[] call;
// use chunks of 20 (20 segments × 1 API call = 60 calls/min at 3-segment batches,
// well below 1500 RPM even at 500 segments).
async function batchEmbed(texts: string[], chunkSize = 20): Promise<number[][]> {
  const results: number[][] = []
  for (let i = 0; i < texts.length; i += chunkSize) {
    const chunk = texts.slice(i, i + chunkSize)
    const response = await ai.models.embedContent({
      model: 'gemini-embedding-001',
      contents: chunk,
      config: { taskType: 'SEMANTIC_SIMILARITY' },
    })
    const embeddings = response.embeddings ?? []
    if (embeddings.length !== chunk.length) {
      throw new Error(`Expected ${chunk.length} embeddings, got ${embeddings.length}`)
    }
    results.push(...embeddings.map(e => e.values ?? []))
  }
  return results
}
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `ai.models.embedContent()` | The single method for all embedding work in `@google/genai` v2. No separate batch method — pass an array of strings to `contents[]` for multi-input in one API call. | Embedding both the user topic and transcript segment texts. |
| `contents: string[]` parameter | Accepts 1–N strings per call; returns one embedding per input string in `response.embeddings[]`. Replaces the v1 single-string `model.embedContent(text)` pattern. | Batching 20 segments per call to stay inside rate limits. |
| `response.embeddings[i].values` | A `number[]` (float array, length 768 for gemini-embedding-001) representing the semantic vector for input `i`. | Computing cosine similarity between topic vector and each segment vector. |
| `taskType: 'SEMANTIC_SIMILARITY'` | Config hint telling the model to optimize vector geometry for comparing two texts directly. Other values (RETRIEVAL_DOCUMENT, RETRIEVAL_QUERY) skew the space for asymmetric search. | Use this for cosine similarity scoring between topic and segment. |
| `cosineSimilarity(a, b)` | Pure math function — dot product divided by product of magnitudes. Returns 0–1 for normalized float vectors. No external library needed. | The scoring function applied per segment after all embeddings are computed. |

### Common Pitfalls

1. **Using `text-embedding-004` — it was shut down January 14, 2026.** Any call to `model: 'text-embedding-004'` will return a 404/model-not-found error. The CONTEXT.md D-01 references this model by name, but the replacement is `gemini-embedding-001`. Use `gemini-embedding-001` everywhere in the implementation; the API call syntax is identical.

2. **Treating `contents` as a single string instead of an array.** The v2 `embedContent()` `contents` param expects `string[]` (or `Content[]`). Passing a bare string `contents: text` works for a single call in some versions but produces ambiguous behavior when the string is interpreted as an iterable — always use `contents: [text]`. The v1 SDK accepted a plain string; v2 changed this.

3. **Reading `result.embedding` instead of `result.embeddings[0].values`.** The v1 SDK returned `result.embedding.values`. The v2 SDK returns `result.embeddings` (plural, array). Accessing `.embedding` on a v2 response returns `undefined` silently — the cosine similarity then operates on empty arrays and always returns 0, making every similarity score 0 with no error thrown.

4. **Running `Promise.all()` over all 500 segments in one burst.** At 500 unconstrained concurrent `embedContent()` calls, you will spike well above 1500 RPM and receive HTTP 429 errors. The `batchEmbed()` pattern above (sequential chunks of 20 strings per call = 25 total API calls for 500 segments) avoids this entirely without needing a sleep or rate-limiter library.

5. **Comparing embeddings from different `taskType` values.** If you embed the topic with `taskType: 'RETRIEVAL_QUERY'` and segments with `taskType: 'RETRIEVAL_DOCUMENT'`, the vectors are in different optimized subspaces — cosine similarity scores are meaningless cross-type. Use `SEMANTIC_SIMILARITY` for both the topic and all segments, which places both in the same symmetric space designed for direct comparison.

## 4. Implementation Guidance

**Model Configuration:**

```
Model:          gemini-embedding-001
Task type:      SEMANTIC_SIMILARITY
Dimensions:     768 (default — do not set outputDimensionality unless reducing for storage)
Input limit:    2048 tokens per string (segments are ~10–50 tokens; well within limit)
Rate limit:     ~1500 RPM free tier; chunk strategy keeps actual usage ~25–30 calls/job
Threshold:      cosine similarity ≥ 0.75 (calibrate — text-embedding-004 community reports
                that semantic similarity scores cluster 0.6–0.9 for topically related text;
                0.75 is a reasonable mid-point; surface as a named constant SEMANTIC_THRESHOLD)
Cap:            MAX_SEMANTIC_MATCHES = 10 (sort by score descending, take top 10 above threshold)
```

**Core Pattern:**

```typescript
// worker/src/semanticMatcher.ts — complete implementation skeleton

import { GoogleGenAI } from '@google/genai'
import type { TranscriptSegment, ClipMatch } from './types.js'

const ai = new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY ?? '' })

const EMBEDDING_MODEL     = 'gemini-embedding-001'  // text-embedding-004 shut down Jan 14 2026
const SEMANTIC_THRESHOLD  = 0.75                     // cosine similarity floor
const MAX_SEMANTIC_MATCHES = 10                      // cap to bound video length
const EMBED_CHUNK_SIZE    = 20                       // strings per embedContent() call

// Embed N strings in sequential chunks — avoids 429s under 1500 RPM free tier
async function batchEmbed(texts: string[]): Promise<number[][]> {
  const results: number[][] = []
  for (let i = 0; i < texts.length; i += EMBED_CHUNK_SIZE) {
    const chunk = texts.slice(i, i + EMBED_CHUNK_SIZE)
    const response = await ai.models.embedContent({
      model: EMBEDDING_MODEL,
      contents: chunk,                               // string[] — one embedding per element
      config: { taskType: 'SEMANTIC_SIMILARITY' },  // symmetric space for direct comparison
    })
    const embeddings = response.embeddings ?? []
    if (embeddings.length !== chunk.length) {
      throw new Error(
        `embedContent chunk mismatch: expected ${chunk.length}, got ${embeddings.length}`,
      )
    }
    results.push(...embeddings.map(e => e.values ?? []))
  }
  return results
}

// Pure cosine similarity — no library dependency
function cosineSimilarity(a: number[], b: number[]): number {
  let dot = 0, magA = 0, magB = 0
  for (let i = 0; i < a.length; i++) {
    dot  += a[i] * b[i]
    magA += a[i] * a[i]
    magB += b[i] * b[i]
  }
  return magA === 0 || magB === 0
    ? 0
    : dot / (Math.sqrt(magA) * Math.sqrt(magB))
}

// Main export — called from worker/src/index.ts when job.semanticEnabled is true
export async function findSemanticMatches(
  segments: TranscriptSegment[],
  topic: string,
): Promise<ClipMatch[]> {
  if (!process.env.GEMINI_API_KEY) {
    console.warn('  GEMINI_API_KEY not set — skipping semantic matching (soft-fail)')
    return []
  }

  // Embed topic + all segments in the same SEMANTIC_SIMILARITY space
  const topicVec = (await batchEmbed([topic]))[0]
  const segTexts  = segments.map(s => s.text)
  const segVecs   = await batchEmbed(segTexts)

  // Score each segment, filter by threshold, cap at MAX_SEMANTIC_MATCHES
  const scored = segments.map((seg, i) => ({
    seg,
    idx: i,
    score: cosineSimilarity(topicVec, segVecs[i]),
  }))

  return scored
    .filter(s => s.score >= SEMANTIC_THRESHOLD)
    .sort((a, b) => b.score - a.score)
    .slice(0, MAX_SEMANTIC_MATCHES)
    .map(({ seg, idx, score }) => ({
      startMs:        Math.round(seg.offset * 1000),
      endMs:          Math.round((seg.offset + seg.duration) * 1000),
      text:           seg.text,
      segmentIndices: [idx],
      matchType:      'semantic' as const,   // ClipMatch extension from D-05
      confidence:     Math.round(score * 100) / 100,  // 2 decimal places
    }))
}
```

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs (TypeScript)

Embedding calls return raw `number[]` arrays — there is no schema to validate on the Gemini response itself. The structured output concern for this module is the `ClipMatch` shape returned by `findSemanticMatches()`. Use a TypeScript interface guard to validate the embedding response before computing similarity, and validate each `ClipMatch` at construction time.

**Type extension — add to `worker/src/types.ts` and mirror in `src/types/job.ts`:**

```typescript
// Extend ClipMatch with Phase 6 fields (D-05)
export interface ClipMatch {
  startMs:        number
  endMs:          number
  text:           string
  segmentIndices: number[]
  // Phase 6 additions — optional so exact-match code needs no change
  matchType?:     'exact' | 'semantic'
  confidence?:    number   // cosine similarity 0–1, 2 decimal places
}
```

**Runtime guard — validate the embedding response before using it:**

```typescript
function assertValidEmbedding(values: number[] | undefined, context: string): number[] {
  if (!values || values.length === 0) {
    throw new Error(`Empty embedding returned for: ${context}`)
  }
  // gemini-embedding-001 default is 768 dimensions
  if (values.length !== 768) {
    console.warn(`Unexpected embedding dimension ${values.length} (expected 768) for: ${context}`)
  }
  return values
}

// Usage inside batchEmbed():
results.push(...embeddings.map((e, idx) =>
  assertValidEmbedding(e.values, `chunk item ${idx}`)
))
```

**Retry logic:** Transient 429 or 503 errors — retry once with 2-second delay (same pattern as `notesGenerator.ts`). Structural errors (empty `embeddings` array, missing `values`) should throw immediately rather than retry — they indicate a model or config problem, not a transient rate limit.

```typescript
// Retry wrapper — mirrors notesGenerator.ts pattern
const sleep = (ms: number) => new Promise<void>(res => setTimeout(res, ms))

async function embedWithRetry(texts: string[]): Promise<number[][]> {
  for (let attempt = 0; attempt <= 1; attempt++) {
    try {
      return await batchEmbed(texts)
    } catch (err: unknown) {
      const is429 = err instanceof Error && err.message.includes('429')
      if (attempt === 0 && is429) {
        console.warn('  Gemini embed 429 — retrying in 2s...')
        await sleep(2000)
      } else {
        throw err   // surface non-429 errors and second attempts
      }
    }
  }
  throw new Error('unreachable')
}
```

### Async-First Design

`ai.models.embedContent()` returns a `Promise` — the module must be fully async. The worker runs in Node.js with top-level `await` available (ESM module with `"type": "module"` in `worker/package.json`).

**How async works in this module:**

- `batchEmbed()` is `async` and uses sequential `await` inside a `for` loop — this is intentional. Each chunk awaits before the next chunk starts, preventing burst-firing all chunks simultaneously and exceeding the RPM limit.
- `findSemanticMatches()` is the single exported `async` function. The caller in `index.ts` uses `await findSemanticMatches(...)` inside an already-async job-processing function.

**The one critical mistake — `Promise.all()` over all segments:**

```typescript
// WRONG — fires all chunks simultaneously, hits 429 under rate limit
const allVecs = await Promise.all(
  segments.map(seg => embedSingle(seg.text))
)

// CORRECT — sequential chunks, stays inside RPM ceiling
const allVecs = await batchEmbed(segTexts)  // sequential for-loop inside
```

At 500 segments and chunk size 20, `batchEmbed()` makes 25 sequential API calls. That takes roughly 2–4 seconds (100–200ms per call) — acceptable for a background worker job. Parallelizing with `Promise.all()` at that scale risks 429 errors on the free tier.

**Soft-fail pattern — semantic failure must not fail the job:**

```typescript
// In index.ts — semantic error is caught, job continues with exact matches only
if (job.semanticEnabled) {
  try {
    semanticMatches = await findSemanticMatches(segments, job.topic)
  } catch (err) {
    console.error('Semantic matching failed (soft-fail, exact matches preserved):', err)
  }
}
```

<!-- Not applicable for embedding-only use case — no generative prompt. -->
Embeddings are deterministic given a model version — no prompt engineering needed. The topic string is embedded as-is (normalized per existing matcher.ts normalize() function).

### Cost and Latency Budget

**Model:** gemini-embedding-001 (replaces shut-down text-embedding-004)

**Free tier:** Google's Gemini API free tier covers embedding calls at no cost up to the quota limit (~1500 RPM based on CONTEXT.md D-01; verify current limit in [AI Studio rate limits](https://aistudio.google.com/rate-limit)). For v1 usage volumes, embedding costs are $0 — the free tier is sufficient.

**Paid tier if free tier is exhausted:** $0.15 per million input tokens (standard). At ~50 tokens per segment × 500 segments = 25,000 tokens per job, that is $0.00375 per job — negligible even at scale.

**Per-job latency estimate (500 segments):**

| Step | Call count | Estimated time |
|------|-----------|----------------|
| Embed topic (1 string, 1 call) | 1 API call | ~150ms |
| Embed 500 segments (25 chunks of 20) | 25 API calls sequential | ~3–5s |
| Cosine similarity computation (500 × 768 ops) | CPU only | <10ms |
| **Total added latency per job** | | **~3–5 seconds** |

This is acceptable for a background worker job — the user has already submitted and is waiting asynchronously.

**Caching strategy:**

- Embedding calls are deterministic given the same model version and input string — the topic embedding can be computed once and reused across all segment comparisons within a job (already the case in the pattern above — `topicVec` is computed in one call).
- There is no cross-job caching needed at v1 scale (each job has a different topic).
- If the same transcript is re-processed (e.g., a job is retried), segment embeddings would be recomputed. This is acceptable — there is no vector store in scope for Phase 6. Caching in a vector DB is a Phase 7+ concern.

**Sub-task routing:** No cheaper model for classification or routing is needed — there is no LLM call in this module, only embedding API calls. The cosine similarity threshold itself acts as the "classifier" (deterministic math, zero cost).

## 5. Evaluation Strategy

### Dimensions

All rubrics start from the domain ingredients in Section 1b. Measurement defaults to code-based (deterministic cosine math) unless the dimension is inherently subjective.

---

**Dimension 1: Exact-Match Integrity (MAT-03)**
Priority: **Critical**

> PASS: Every segment index present in `exactMatches` (output of `buildClipPlan()`) also appears in the final `clipPlan` array after semantic deduplication. The `dedupedSemantic` filter removes only segments whose `segmentIndices` overlap with exact-match indices — it never removes the exact-match entries themselves.
>
> FAIL: Any segment returned by `buildClipPlan()` is absent from the final `clipPlan`, regardless of its cosine score or whether a semantically similar segment was also found. A missing exact match is a silent correctness regression — the student searched a term spoken verbatim in the video and does not receive it.
>
> Measurement: **Code** — unit test asserts `clipPlan` is a superset of `exactMatches` by segment index. Run on every PR.

---

**Dimension 2: Toggle Isolation — Opt-In Default Preserved (SUB-04)**
Priority: **Critical**

> PASS: When `job.semanticEnabled` is `false` (the default), `findSemanticMatches()` is never called. The final `clipPlan` contains only `matchType: 'exact'` entries. No embedding API calls are made. This holds even if the submission form is manipulated (Zod schema coerces the checkbox value; `@default(false)` on the Prisma column is the authoritative default).
>
> FAIL: A `ClipMatch` with `matchType: 'semantic'` appears in the clip plan for a job where `semanticEnabled` was not explicitly set to `true`, OR `findSemanticMatches()` is called (incurring API cost and latency) for an opt-out job.
>
> Measurement: **Code** — unit test with `job.semanticEnabled = false`; assert `findSemanticMatches` is never invoked and `clipPlan` contains zero `matchType: 'semantic'` entries.

---

**Dimension 3: Retrieval Precision at Threshold (MAT-02)**
Priority: **High**

> PASS: For a given (YouTube video, topic) test triple, every segment in the returned semantic matches is judged as conceptually relevant by a subject-matter label — meaning an instructional designer would include it in a targeted study guide for that exact topic, not merely the subject area. On-topic rate ≥ 0.70 across the reference dataset (i.e., ≥ 70% of returned semantic matches are genuinely relevant to the queried topic).
>
> FAIL: On-topic rate falls below 0.70, OR any single test case returns a segment from a clearly different discipline (e.g., economics segment returned for a machine-learning topic query), OR a segment that shares vocabulary with the topic but addresses a different concept is returned at high confidence.
>
> Measurement: **Code** (cosine score computation + threshold enforcement) + **Human** (on-topic labeling of reference dataset). The 0.75 cosine threshold is the primary filter; human review of the reference dataset determines whether the threshold is appropriately calibrated.

---

**Dimension 4: False Positive Rate — Cross-Discipline and Adjacent-Concept Inflation**
Priority: **High**

> PASS: For topics with known adjacent concepts (e.g., "gradient descent" neighbors "backpropagation", "loss function", "learning rate"), the returned segment set is focused on the stated topic. Adjacent concepts are not returned unless the segment explicitly addresses the queried topic within the same explanation. No segment from a different subject domain (e.g., economics in a machine-learning video) is returned above threshold.
>
> FAIL: The reference dataset adversarial cases — including at least 3 triples with adjacent-concept and cross-discipline false-positive risk — show precision below 0.60, OR any cross-discipline segment scores above `SEMANTIC_THRESHOLD`.
>
> Measurement: **Code** (score filtering at threshold) + **Human** (reference dataset adversarial labels). LLM judge is not used here — the reference dataset is small enough for direct human review.

---

**Dimension 5: Proportionality — Match Count vs. Topic Scope**
Priority: **Medium**

> PASS: A narrow, specific topic (e.g., "softmax function") returns 1–4 semantic matches. A broad topic (e.g., "deep learning") may return up to the 10-match cap, but each returned segment addresses a distinct sub-concept. The `MAX_SEMANTIC_MATCHES = 10` cap is never exceeded. No match has `startMs >= endMs`.
>
> FAIL: A narrow topic returns ≥ 8 semantic matches because low-relevance filler segments score above threshold, OR the cap is exceeded due to a code bug, OR `startMs >= endMs` appears in any returned match (malformed segment boundary).
>
> Measurement: **Code** — assert `results.length <= MAX_SEMANTIC_MATCHES`, assert `startMs < endMs` for all entries, assert cosine scores of returned segments are all `>= SEMANTIC_THRESHOLD`.

---

**Dimension 6: Confidence Indicator Honesty (MAT-04)**
Priority: **Medium**

> PASS: The `confidence` field on each `ClipMatch` stores the raw cosine similarity rounded to 2 decimal places (e.g., `0.81`), and any UI display converts this to a relative qualitative label (e.g., "Strong match" for ≥ 0.85, "Related" for 0.75–0.84) rather than presenting "81%" as a validated accuracy percentage. The `matchType: 'semantic'` label visually distinguishes semantic matches from exact matches in the transcript view.
>
> FAIL: The raw cosine score is displayed directly to the student as a percentage (e.g., "81% match") without contextual framing, implying a calibrated accuracy the system does not have. Or `matchType` is absent from the returned `ClipMatch` objects, making it impossible to distinguish semantic from exact matches.
>
> Measurement: **Code** — assert `matchType === 'semantic'` and `confidence` is a number between 0 and 1 on every returned object. UI display format is a design decision reviewed once during implementation (Human, one-time). No ongoing LLM judge needed.

---

**Dimension 7: Soft-Fail Integrity**
Priority: **Critical**

> PASS: When `findSemanticMatches()` throws (Gemini API error, 429, empty embedding response, network timeout), the error is caught in `index.ts`, a warning is logged, and the job completes successfully with `exactMatches` only. The student receives their exact-match clip plan. No job status is set to failed solely because of a semantic matching error.
>
> FAIL: An exception from `findSemanticMatches()` propagates uncaught and causes the job to enter an error state, leaving the student with no output even though exact matches were available.
>
> Measurement: **Code** — unit test that mocks `findSemanticMatches` to throw; assert job completes with `exactMatches` only and status is not failed.

---

### Reference Dataset

**Size:** 12–15 labeled triples. Minimum 12, target 15 before deployment.

**Composition:**

| Category | Count | Description |
|----------|-------|-------------|
| True positive — narrow topic | 3 | (video, topic, expected segments) where a specific technical term has clear conceptual relatives in the transcript. Example: "gradient descent" in a PyTorch tutorial. Expected: 2–4 relevant segments. |
| True positive — broad topic | 2 | Topic spans multiple sub-concepts. Example: "neural networks" in a deep learning lecture. Expected: up to 10 matches, each distinct. |
| Adjacent-concept adversarial | 3 | Topics whose neighbors are close but distinct. Example: "softmax" in a lecture that also covers "cross-entropy loss". Expected: only softmax segments returned; loss-function segments excluded. |
| Cross-discipline adversarial | 2 | Topic from one discipline in a video that covers a neighboring field. Example: "gradient" in an economics lecture that also discusses calculus. Expected: zero or flagged false positives. |
| Zero-match case | 2 | Topic that is genuinely absent from the transcript. Expected: empty result set (no segment scores above 0.75). |
| Exact-match overlap case | 2 | Topic that has both verbatim mentions and semantic relatives. Expected: exact matches in `exactMatches`, semantic relatives in `dedupedSemantic`, no duplicates. |
| Edge case — very short transcript | 1 | Video with < 5 segments total. Expected: graceful handling, no index errors. |

**Labeling approach:** Human review (product owner or engineer with subject knowledge) labels each triple with:
- `expectedOnTopicCount`: integer — how many returned segments should be on-topic
- `expectedZeroMatches`: boolean — for zero-match cases
- `adversarialFalsePositiveSegments`: segment texts that must NOT appear in results

No LLM judge for labeling in v1. The dataset is small enough for direct human review, and LLM judge calibration against human scores (required before trusting a judge per ai-evals.md) is not worth the overhead at this scale.

**Creation timeline:** Build the dataset concurrently with implementation of `semanticMatcher.ts`, not after. The `semantic-eval-dataset.json` fixture file should exist before the first manual test of the module. Use publicly available YouTube educational videos with stable transcripts (e.g., MIT OpenCourseWare, 3Blue1Brown, Khan Academy).

## 6. Guardrails

### Online (Real-Time)

These run synchronously in the job-processing path on every semantic-enabled job. Each is implemented in code — no LLM call, no network request beyond what the feature already requires.

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Exact-match integrity | After `dedupedSemantic` is computed: check that every index in `exactMatches.flatMap(m => m.segmentIndices)` is still present in the final `clipPlan` | Throw an internal error before writing `clipPlan` to the database; log the discrepancy. The job enters a failed state with a clear error code (not a silent success with missing clips). This is preferable to silently delivering an incomplete plan — the student can resubmit. |
| Max-match cap enforcement | After scoring: `slice(0, MAX_SEMANTIC_MATCHES)` before any merge | Enforced in `findSemanticMatches()` before returning — the cap is structural, not a guardrail check. Validated by the code-based test in Dimension 5. |
| Semantic API soft-fail | `findSemanticMatches()` throws for any reason (429, empty embedding, network error) | Catch in `index.ts`, log with `console.error`, continue with `exactMatches` only. Do not set job status to failed. Log includes: error message, job ID, topic string (truncated to 100 chars), and segment count for debugging. |
| Toggle integrity | Before calling `findSemanticMatches()`: assert `job.semanticEnabled === true` | Enforced by the `if (job.semanticEnabled)` guard in `index.ts`. The Prisma `@default(false)` and Zod `z.coerce.boolean().default(false)` are the upstream enforcement points. |

### Offline (Flywheel)

These run on a sampled batch — not per-request. At v1 volume (low, anonymous), "sampling" means a developer manually reviews a batch of recent semantic-enabled jobs periodically (weekly or after any threshold or model change).

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|-----------------------|
| On-topic rate | Review 10 most recent semantic-enabled jobs; for each, manually judge whether returned semantic matches are conceptually relevant to the submitted topic. Target: ≥ 70% of matches are on-topic. | If rate falls below 70% over 2 consecutive review cycles: lower `MAX_SEMANTIC_MATCHES` from 10 to 5 as an immediate mitigation, then investigate threshold recalibration (raise `SEMANTIC_THRESHOLD` from 0.75 toward 0.80). |
| False positive rate — cross-discipline | In each sampled batch, flag any match where the segment text is clearly from a different subject area than the submitted topic. Target: 0 cross-discipline false positives in the sample. | Any confirmed cross-discipline false positive triggers a threshold review. If reproducible: raise `SEMANTIC_THRESHOLD` by 0.03 increments and re-run reference dataset eval before deploying. |
| Score distribution drift | Track the distribution of cosine scores for returned matches (mean, min, max) in Railway logs. If mean score drifts below 0.78 (i.e., many borderline 0.75–0.77 matches), the threshold may be too permissive. | If mean returned score drops below 0.78 in a batch: review whether the topic inputs have become shorter or noisier (students submitting single words vs. phrases). Consider normalizing topic input (already handled by existing `normalize()` in `matcher.ts`). |
| Exact-match integrity (post-deploy verification) | On each deployment that touches `semanticMatcher.ts` or `index.ts`: manually run one end-to-end job with a topic that is verbatim in the transcript AND has semantic matches, and verify both appear in `clipPlan`. | Any regression: immediate rollback. This is a critical-priority dimension. |
| Semantic opt-in usage rate | Count jobs with `semanticEnabled = true` vs. total jobs in Railway logs (weekly). | If usage rate is below 5%: the toggle may be confusing or buried; consider UX copy improvements. If usage rate is above 60%: semantic mode may be becoming the de facto default, which warrants reconsideration of whether it should remain opt-in. |


**Key Metrics to Track (via Railway log stream, v1):**

Each semantic-enabled job should emit a structured log line on completion:

```typescript
// Emit after semantic matching completes (or soft-fails) in index.ts
console.log(JSON.stringify({
  event:          'semantic_matching_complete',
  jobId:          job.id,
  semanticEnabled: job.semanticEnabled,
  exactMatchCount: exactMatches.length,
  semanticMatchCount: dedupedSemantic.length,
  softFail:       semanticFailed,           // boolean — true if findSemanticMatches threw
  topScores:      topThreeScores,           // number[] — top 3 cosine scores, or [] on soft-fail
  durationMs:     Date.now() - startTime,
}))
```

Metrics surfaced by querying this log line in Railway:

| Metric | What It Signals |
|--------|-----------------|
| `semanticMatchCount` per job | Baseline match volume; sudden spike may indicate threshold too permissive after a model change |
| `softFail: true` rate | Gemini API reliability; if > 5% of semantic jobs soft-fail, investigate rate limit or model availability |
| `durationMs` for semantic path | Latency budget; if median exceeds 8 seconds for 500-segment transcripts, chunk strategy may need adjustment |
| `topScores` distribution | Score drift indicator; if top scores trend toward 0.75–0.77 (borderline), threshold may need raising |
| `semanticEnabled` rate | Feature adoption; inputs to UX decisions about toggle placement and copy |

**Alert Thresholds:**

There is no automated alerting in v1 (zero-cost constraint; Railway does not provide native log-based alerts on the free plan). These are manual review triggers — checked weekly or after any deployment touching Phase 6 code:

| Condition | Manual Review Trigger |
|-----------|----------------------|
| `softFail: true` in > 5% of semantic jobs in a week | Check Gemini API quota usage in AI Studio; check for 429s in logs |
| `semanticMatchCount` average > 8 per job | Threshold may be too permissive; run reference dataset eval and consider raising to 0.78 |
| `durationMs` median > 8000ms (8 seconds) for the semantic path | Check whether transcript lengths have increased; review chunk strategy |
| `exactMatchCount` = 0 AND `semanticMatchCount` = 0 for > 30% of jobs | May indicate topic normalization issue or a model change affecting embedding space |
| Any job log where `exactMatchCount` before merge != `exactMatchCount` in final `clipPlan` | Exact-match integrity regression — deploy hotfix immediately |

**Smart Sampling Strategy:**

At v1 volume (anonymous, low-traffic), all semantic-enabled jobs are effectively sampled — there are few enough that a developer can review logs directly. As volume grows:

1. Prioritize review of jobs where `softFail: true` — these need diagnosis.
2. Prioritize review of jobs where `semanticMatchCount >= 9` — these may indicate threshold-creep or adjacent-concept inflation.
3. Prioritize review of jobs where `exactMatchCount > 0` — these are the overlap cases that test exact-match integrity under real conditions.
4. Deprioritize jobs where `semanticMatchCount = 0` and `softFail: false` — the threshold correctly rejected all segments; no quality concern.

When adopting Langfuse: configure session-level traces per job and add a `score()` call after any manual quality review, building a ground-truth dataset from production over time rather than relying solely on the curated reference dataset.
